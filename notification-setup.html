Responder Notification Setup

A practical guide to how individual responders configure the way they get paged in Grafana Cloud IRM — personal notification rules, the mobile app, phone/SMS, ChatOps linking — and how admins drive adoption at scale. This is the foundation the rest of IRM depends on: a perfectly designed schedule and escalation chain page nobody if the person on-call never set up how they're reached. Companion to the On-Call Schedules, Escalation Chains, Integrations, Insights, and Incident Management guides.

1. Why this matters most#1-why-this-matters-most

Chains and schedules decide *who and when*. Personal notification rules decide *how* — which of a responder's devices and apps actually ring. If that last step is missing, everything upstream fails silently.

The single most important fact to internalise: email is the default channel for every user. A responder who configures nothing else can only be reached at the email address on their Grafana account — no push, no SMS, no call. This is the number-one onboarding gap, and it fails quietly: the schedule looks healthy, the chain fires, and the page lands in an inbox nobody is watching at 3am.

2. The two chains: Default and Important#2-the-two-chains-default-and-important

Every responder configures notification rules in Profile → IRM tab → Notification rules (also editable from the IRM mobile app's Settings tab). There are two separate, independently configured chains:

  • Default notification rules — used for standard escalation events. Best kept less intrusive (Slack, email, push).
  • Important notification rules — triggered when an escalation step is marked "important." These bypass the Default chain entirely, so they should be the loud, hard-to-miss methods (critical push, phone call, SMS).

An escalation step's Default / Important toggle is what selects which of the responder's two chains fires. A step marked important runs the person's Important rules and skips their Default rules. Because Important is the escape hatch that pierces DND and calls phones, use it sparingly in chain design — overuse erodes the signal (see the Escalation Chains guide).

Both chains must be configured.

A responder with only a Default chain gets nothing extra when a critical alert marks a step important — it simply falls back to whatever Default holds, or to email.

3. Building a chain#3-building-a-chain

In the Notification rules UI, each step is either a Notify by (a delivery method) or a Wait (a timing gap). Add steps, then drag to reorder; they execute top to bottom from position 0.

Available notification methods:

MethodWhen to reach for it
Mobile push (default)Recommended primary channel
Mobile push important / criticalLoud, DND-piercing — for the Important chain
Slack / Microsoft Teams / TelegramFast, low-friction messaging
SMSBackup for critical alerts
Phone callLast-resort, hard-to-ignore
EmailNon-urgent / summary only
Webhook (personal)Custom personal automation
Wait

steps use a fixed set of durations: 1, 5, 15, 30, or 60 minutes (60/300/900/1800/3600 seconds). There is no automatic per-method retry — you build fallback yourself by chaining a notify, then a wait, then a louder notify.

A sensible Default chain (from the docs): Slack immediately → mobile push after 5 minutes → SMS after 15 minutes → phone call after 30 minutes.

A sensible Important chain: critical mobile push immediately → SMS after 1 minute → phone call after 5 minutes.

The principle: layer from least intrusive to most intrusive, with waits between, so you escalate your *own* attention automatically.

4. The IRM mobile app#4-the-irm-mobile-app

The mobile app should be most responders' primary channel — it's the most reliable and the only one that can pierce Do Not Disturb cleanly. Note it has no offline support; it needs connectivity to receive pushes.

Install and pair.

Search "Grafana" in the App Store or Google Play. Sign in either by entering your stack URL (e.g. yourstack.grafana.net) and authenticating with Grafana.com credentials, or by tapping "connect app via QR code" and scanning the QR from your Grafana Cloud profile. Add multiple stacks via the Connected accounts screen if you span environments.

Two push types

, which you add to your notification rules like any other method: *Mobile push default* (follows the app's Default notification settings) and *Mobile push important* (louder/urgent, uses Important settings).

Critical alerts — the step people miss:

  • iOS: enable Critical Alerts at the OS level (Settings → Notifications → Grafana IRM → Critical Alerts), then enable "Override DND for important" in-app. Without the OS toggle, important pushes are just normal pushes.
  • Android: each notification type maps to a system notification channel; set DND override and sound per-channel via "Customize notifications," and toggle "Override system volume" in-app. Prefer Pixel or Samsung devices — some manufacturers (Xiaomi, OnePlus) aggressively suppress notifications. If pushes are unreliable, disable "Pause app activity if unused" and set Battery to Unrestricted.
Sync the IRM contact

(Settings → Sync Grafana IRM contact) to create a phone contact holding all IRM numbers, so calls are recognisable and can be set to bypass DND via iOS Emergency Bypass.

Always send a test notification

(Settings → Push notifications → Send test notification, for both Default and Important) after setup. Untested is unconfigured.

The app also shows your on-call status and upcoming shifts, and lets you create and accept shift swaps on the go, with pushes for swap requests and for shifts starting within 15 minutes.

5. Phone, SMS, and ChatOps linking#5-phone-sms-and-chatops-linking

Phone verification

(Profile → IRM tab → Phone verification): enter your number in E.164 format — +, country code, local number, no spaces/dashes/parentheses, and drop any national trunk 0 (UK 020… becomes +4420…). Get the code by SMS ("Send verification code") or automated voice call ("Call to get the code" — use this for landlines). Then add SMS or Phone call steps to your chains.

Worth teaching responders about live calls: press 1 to acknowledge, 2 to resolve, 3 to silence 30 minutes, 4 to repeat. Voicemail does *not* acknowledge or resolve — only a live keypress does. SMS bundles additional alerts within a 2-minute window into one message; Default and Important alerts bundle separately. Calls and SMS incur no extra cost, but a few regions are unsupported (Crimea, Cuba, Iran, North Korea, Syria). Add the IRM source numbers to your contacts so pages are recognisable.

Personal ChatOps linking

(Profile → IRM tab; each requires an admin to have installed the integration first):

  • Slack — Slack connection → authorise your account. Required for auto-updated on-call Slack user groups and @mentions.
  • Microsoft Teams — MS Teams connection → send the linkUser command to the IRM bot.
  • Telegram — Telegram connection → send the verification code to the bot.
Admin fallback

a user who can't self-verify a phone can be marked verified by an admin holding the User Settings Admin RBAC role (IRM → Users → user → Overview → Phone connector → Mark as verified). Paid orgs only.

6. Roles: who can actually be paged#6-roles-who-can-actually-be-paged

Responders need the right role, or they won't receive notifications. Basic roles are Viewer (read-only), Editor, and Admin. For notification purposes the accurate framing is via RBAC:

  • A plain Viewer/Reader is read-only and isn't set up as an active responder.
  • OnCaller is the role "designed for on-call responders" — read access to IRM resources plus the ability to edit alert groups, schedules, shift swaps, and their own user settings.
  • Notifications Receiver — "can receive alert notifications and edit their own IRM user settings" — is the minimal responder grant, optionally paired with User Settings Editor.

Assign OnCaller (or Notifications Receiver) to anyone who goes on-call. Admins also control which channels exist: a channel must be installed under IRM → Integrations *and* enabled under IRM → Settings → Admin & API before it appears in users' personal rules.

7. Driving adoption at scale#7-driving-adoption-at-scale

Because email-only fails silently, adoption is an active job, not an assumption. The recommended sequence (from the notify-responders overview):

  1. Ensure all users have configured notification channels.
  2. Each responder sets up both Default and Important rules.
  3. Build escalation chains that reference them.
  4. Mark critical steps "important."
  5. Test the full flow end to end with a non-production alert.
Spotting gaps.

There is no built-in "users without notification rules" report, so checking is per-user: IRM → Users → a user's Overview tab shows their Phone connector, Mobile App connector, and linked Slack. Admins can see linked Slack profiles across all users from the Users list. The scalable alternative is to provision baseline rules centrally as code (next section) rather than relying on each individual.

Make it part of onboarding.

Bake "configure IRM notification rules, install the mobile app, verify your phone, send a test notification" into the checklist for every new team member — the same day they're added to a schedule.

8. Notification rules as code#8-notification-rules-as-code

Personal notification rules are manageable as code — the scalable way to guarantee every responder has a working baseline instead of hoping they set one up.

Terraform

The grafana_oncall_user_notification_rule resource (requires OnCall provider ≥ v1.8.0) models one step. Look up each user with the grafana_oncall_user data source, then define their chain. The two chains are distinguished purely by important = true/false, and position restarts at 0 within each chain.

terraform
data "grafana_oncall_user" "my_user" {
  provider = grafana.oncall
  username = "my_username"
}

# --- Default chain ---
resource "grafana_oncall_user_notification_rule" "default_1" {
  provider = grafana.oncall
  user_id  = data.grafana_oncall_user.my_user.id
  position = 0
  type     = "notify_by_mobile_app"
}

resource "grafana_oncall_user_notification_rule" "default_2" {
  provider = grafana.oncall
  user_id  = data.grafana_oncall_user.my_user.id
  position = 1
  duration = 600 # 10 minutes
  type     = "wait"
}

resource "grafana_oncall_user_notification_rule" "default_3" {
  provider = grafana.oncall
  user_id  = data.grafana_oncall_user.my_user.id
  position = 2
  type     = "notify_by_phone_call"
}

# --- Important chain ---
resource "grafana_oncall_user_notification_rule" "important_1" {
  provider  = grafana.oncall
  user_id   = data.grafana_oncall_user.my_user.id
  important = true
  position  = 0
  type      = "notify_by_mobile_app_critical"
}

resource "grafana_oncall_user_notification_rule" "important_2" {
  provider  = grafana.oncall
  user_id   = data.grafana_oncall_user.my_user.id
  important = true
  position  = 1
  duration  = 300 # 5 minutes
  type      = "wait"
}

resource "grafana_oncall_user_notification_rule" "important_3" {
  provider  = grafana.oncall
  user_id   = data.grafana_oncall_user.my_user.id
  important = true
  position  = 2
  type      = "notify_by_phone_call"
}

Step type values: notify_by_mobile_app, notify_by_mobile_app_critical, notify_by_sms, notify_by_phone_call, notify_by_slack, notify_by_telegram, notify_by_msteams (Cloud only), notify_by_email, and wait (with duration from the fixed set 60/300/900/1800/3600). Import existing rules with terraform import grafana_oncall_user_notification_rule.name "{{ id }}".

Provision a whole team

by pairing grafana_oncall_user with a for_each over a list of usernames and a module that stamps out the same baseline Default and Important chains for everyone — the reliable answer to "make sure everyone has rules." Responders can still add personal preferences on top; a code-managed baseline just guarantees nobody is email-only.

API

The OnCall HTTP API exposes personal_notification_rules — note it requires user-scoped authentication (a user API token, not an org token) and the user-settings permission:

  • POST {{API_URL}}/api/v1/personal_notification_rules/ — body: user_id (required), type (required), position (optional; -1 appends), duration (for wait), important (default false).
  • GET .../personal_notification_rules/ — filter by user_id, important; returns Default and Important rules together, each with its own position sequence.
  • GET/DELETE .../personal_notification_rules/<ID>/.

As-code best practices

  • Provision a baseline for every responder rather than relying on manual setup — this is the single highest-value use of the resource.
  • Keep it a floor, not a ceiling: let responders refine their own chains on top of the baseline.
  • Version the rules in Git with PR review, alongside the schedules and chains that invoke them.
  • Remember the auth model: notification-rule writes need user-scoped tokens with the user-settings permission — plan your provisioning pipeline's credentials accordingly.

9. Quick reference checklist#9-quick-reference-checklist

For each responder:

  • Assigned the OnCaller (or Notifications Receiver) role
  • Both Default and Important notification rules configured — not email-only
  • Default chain layers non-intrusive → intrusive with Wait steps
  • Important chain uses critical push / phone / SMS
  • Mobile app installed and paired (URL or QR)
  • iOS Critical Alerts enabled / Android per-channel DND + volume set
  • Phone number verified in E.164 format
  • IRM contact synced; DND bypass configured
  • Slack/Teams/Telegram linked as needed
  • Test notification sent on both chains — and it arrived
  • For teams: baseline chains provisioned as code
