Incident Management

A practical guide to declaring, coordinating, resolving, and learning from incidents with Grafana Cloud IRM. Written for platform teams configuring incident response and for the responders who run incidents. Part 5 of the IRM enablement series, following On-Call Schedules, Escalation Chains, Integrations, and Insights.

1. Where incidents fit#1-where-incidents-fit

Grafana IRM brings together two capabilities: OnCall (alert grouping, escalation, schedules, paging) and Incident (the formal incident lifecycle — coordination, timeline, retrospectives). Incidents are the coordination layer *above* alert groups.

text
Alert fires → Alert group (OnCall) → Incident declared → Coordinate → Resolve → Review

Incident management lives under Alerts & IRM → IRM → Incidents; its configuration is under IRM → Settings → Incidents.

Incident vs alert group — know the difference:

AspectAlert groupIncident
CreationAutomatic from alertsManual or via escalation step
PurposeGroup related alertsCoordinate response to a significant event
ScopeTechnical signalsBusiness impact and coordination
LifecycleFiring → Acknowledged → ResolvedCustomizable status progression
CommunicationNotifications to respondersStakeholder updates, dedicated channels

Not every alert deserves an incident. Declare an incident when an event needs coordinated cross-team response, formal or compliance tracking, stakeholder communication, or a post-incident review. Attach the contributing alert groups (up to 5 per incident) to preserve technical context.

2. Declaring an incident#2-declaring-an-incident

Incidents can be declared from wherever the signal first appears:

  • IRM UI — Incidents → Declare incident. Fields: Title (required), Severity, Labels; "More options" reveals Channel prefix, Status, and Start time.
  • Dashboard panel — panel menu → More → Declare incident, so you can declare while looking at the concerning metric.
  • From an alert group — Alert groups → select → Actions → Declare incident.
  • From a firing alert in Grafana Alerting — the Declare incident button on the alert.
  • From Slack — /grafana incident new <severity> <title> opens a modal; submitting creates the incident and its channel.
  • Automatically from an escalation chain — add a Declare incident step (note: only works on non-default routes; configure a specific route for alerts that should auto-declare).
  • API / prefill — the IncidentsService.CreateIncident RPC, plus URL-parameter prefill and a browser bookmarklet.
What declaration triggers

(depending on your integrations): a dedicated Slack channel, notification of relevant responders, generation of the incident timeline, optional conference bridges (Zoom), and optional tickets in external systems (Jira). Title, severity, labels, and status stay editable throughout.

Private incidents

tick "Private incident" for access-restricted coordination — the Slack channel is set private and only the creator sees it until others are added via the Roles panel or invited to the channel. (IRM can't auto-create private Slack channels, so create one manually and invite the Grafana Cloud app first.)

3. Severities, statuses, and workflow#3-severities-statuses-and-workflow

Pre-configured severities:

SeverityMeaning
CriticalUrgently requires immediate attention
MajorSignificant, blocking problem that requires help
MinorMay be affecting customers, but no one is blocked
PendingSeverity to be decided — determine as soon as possible

The default severity on declaration is Pending (configurable). Custom severities carry a Label, a numeric Level (1 = highest), and optional description/icon — note the Level is immutable after creation, so to re-rank, create a new severity and archive the old one. Design severities around your SLAs and team capacity, and map any priority scheme onto them (P1→Critical, P2→Major, P3→Minor, P4→Pending).

Statuses

default to Active and Resolved. You can add custom statuses (name, description, icon, color) that reflect your real process — a common progression teams build is Declared → Acknowledged → Mitigated → Resolved → Closed. The managed-incident workflow stages are Declare → Document → Collaborate → Resolve.

Custom fields

add incident metadata of type Text, Number, Single-select, or Multi-select. Keep the set small, prefer selects for consistency, and mark a field Mandatory only when it truly must be completed before resolution.

4. Roles, participants, and tasks#4-roles-participants-and-tasks

Roles.

Two key roles ship by default: Commander (oversees the incident — communication, tasks, updates) and Investigator (diagnoses and resolves). Add custom roles as needed, flagging the critical ones as key roles. Assign roles from the incident's Roles panel, or in Slack with the Assume role button or /grafana incident assign <role> <user>.

Participants.

Invite individual users or whole teams; invitations go through the Direct Paging integration and reach people via their personal notification rules. Choose Default or Important priority. Participant responses matter: Accepting or Declining resolves the associated alert group and stops escalation; Dismissing leaves it active. Status icons: 🔔 invited, 👁️ acknowledged, ✔️ accepted, ❌ declined.

Tasks / action items.

Track work in the Tasks sidebar (+Task) or Slack (/grafana incident tasks add). Each task is assignable and cycles Todo → In Progress → Done. Tasks can be converted to GitHub or Jira issues (status syncs back), keeping incident coordination and engineering tracking aligned.

5. The timeline: your single source of truth#5-the-timeline-your-single-source-of-truth

The incident timeline is a timestamped chronological record. Add status updates, notes (Markdown; URLs auto-collected into "Links and context"), images/screenshots (PNG/JPG; Cmd/Ctrl+I captures a Grafana screenshot), queries (captured as static snapshots), and dashboard panels.

Slack emoji reactions feed the timeline directly:

  • 🤖 (:robot_face:) — add a message to the timeline
  • 💡 (:bulb:) — create a task / post-incident action item
  • 📢 (:loudspeaker:) — add a status update

Filter the timeline by importance (Highly relevant / All relevant / All activity), time range, or reaction, and search it. Tagging key decisions and actions as you go is what makes the retrospective fast and honest.

Status updates

are distinct from notes: they're the stakeholder-facing milestone communication (impact confirmed, mitigation in progress, resolved). Add them in the UI, via /grafana incident update add, or the 📢 reaction. You can't add status updates to an already-resolved incident, so communicate resolution before closing.

6. ChatOps: running incidents from Slack#6-chatops-running-incidents-from-slack

Install the Grafana Cloud Slack app and have each responder link their Slack profile (Profile → IRM → Slack connection). Configure incident channel behavior under IRM → Integrations → Apps → Slack:

  • Auto-create a channel per incident (the war room), auto-invite users with active roles, and post updates there.
  • Channel name template defaults to {{ prefix }}-{{ date }}-{{ title }} → incident-2024-01-12-database-outage. Variables: prefix, title, date, id. Template changes aren't retroactive.
  • Auto-archive resolved channels after a configurable number of days (30–60 recommended), with a warning posted 24 hours before.

Type /grafana in a channel for context-aware action buttons. Common commands: incident new, incident drill, incident assign/unassign, incident severity, incident update add, incident tasks add, incident resolve <summary>, escalate <user>.

Incident announcements

auto-post incident info (severity, status, roles, labels) to designated channels on declaration and keep it updated. Each announcement channel takes an incident filter using incident query syntax (e.g. severity:critical → #incidents-critical), so you can route by severity, team, or service and separate drills from production. Incident briefings post a custom message (runbooks, checklists, escalation contacts) into a new incident's channel.

Microsoft Teams is supported and managed through the UI; confirm Teams war-room parity directly if your teams use it, as the incident-specific Teams behavior is lightly documented.

7. Labels, service_name, and the Service Center#7-labels-service-name-and-the-service-center

Labels are the connective tissue between incidents and analytics. They arrive three ways: static (set at the integration, applied to all its incidents), dynamic (transferred from the alert group on declaration), and manual (added during the incident). The flow is Alert rule labels → Alert group labels → Incident labels.

Essential labels: service_name (required for Service Center), severity, team, environment. service_name is the linchpin — it flows from alert to alert group to incident, associates incidents with services and SLOs, and powers the Service Center's unified per-service view (on-call handoffs, operational reviews, SLO correlation). Apply it consistently and preserve it through label templates, and per-service incident analytics come for free (see the Insights guide).

8. Resolve and learn#8-resolve-and-learn

Resolving well is what turns an incident into an improvement:

  • Add resolution notes capturing root cause, resolution steps, and lessons learned (/grafana incident resolve <summary> records a resolution summary).
  • Complete the record: finalize the timeline, attach all relevant alert groups, and correct labels — accurate labels mean accurate analytics.
  • Mandatory custom fields must be completed before the incident can be resolved.
  • Review the metrics: MTTR (mean time to resolve) and MTTA (mean time to acknowledge) from IRM Insights, service health against SLOs, and recurring-issue trends.
  • Feed learnings back into the loop: tune alert quality and thresholds, improve escalation chains, update runbooks based on resolution patterns, and add monitoring for earlier detection.

Because Insights reads MTTR from the incident's start and end timestamps, correct those timestamps during the review — the analytics recalculate automatically.

9. Practice with drills#9-practice-with-drills

Run drill incidents to rehearse response without touching production metrics — drills are excluded from dashboards and analytics. Declare one with + Start a drill in the UI, /grafana incident drill <title> in Slack, or isDrill: true via the API. Separate drill and production announcement channels, and run drills regularly to keep the team fluent and validate that integrations still fire.

10. Incident management as code#10-incident-management-as-code

Incident *configuration* — severities, statuses, roles, custom fields, labels, and Slack settings — is managed through the IRM UI or the Incident API, not Terraform. There is no grafana_incident Terraform resource. What *is* codifiable is the automation that declares incidents: the Declare incident escalation step lives on routes and escalation chains, which are Terraform-manageable (grafana_oncall_escalation, grafana_oncall_escalation_chain) — so you can codify *when* incidents get declared even though the incident config itself is UI/API.

The Incident API

A JSON/HTTP RPC API (not REST): every call is an HTTP POST to {base}/{Service}.{Method}.

  • Base: https://your-stack.grafana.net/api/plugins/grafana-irm-app/resources/api/v1/
  • Auth: Authorization: Bearer glsa_... (service account token), Content-Type: application/json
  • Response: every response has an error string (empty = success); lists paginate via a cursor.
  • Official clients: Go (github.com/grafana/incident-go), Node (@grafana/incident-node).

Declare an incident with IncidentsService.CreateIncident:

bash
curl -X POST \
  "https://your-stack.grafana.net/api/plugins/grafana-irm-app/resources/api/v1/IncidentsService.CreateIncident" \
  -H "Authorization: Bearer $GRAFANA_SA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Checkout latency elevated",
    "severity": "major",
    "status": "active",
    "labels": [{ "label": "service_name", "value": "checkout" }],
    "roomPrefix": "inc",
    "isDrill": false
  }'

Severity options are lowercase (pending, minor, major, critical); status is active or resolved (create as resolved to open a retrospective incident).

Nine services cover the surface: IncidentsService (query/get/declare/update, assign roles, update labels), ActivityService (timeline entries — AddActivity, body up to 65,536 chars), TasksService, RolesService, StatusService, FieldsService (custom fields *and* labels, modeled as a "labels" domain), KeyUpdatesService, IntegrationService, and UsersService.

As-code best practices

  • Codify the trigger, configure the rest via API scripts. Manage declare-incident escalation steps in Terraform alongside your chains; script severities, statuses, roles, custom fields, and labels through the Fields/Status/Roles services so incident config is reproducible and reviewable even though it isn't Terraform-native.
  • Version your incident config scripts in Git with PR review, the same discipline as the rest of the series.
  • Use service account tokens with least privilege, and remember IRM user IDs differ from Grafana user IDs (map via the grafana_oncall_user data source when wiring OnCall pieces).
  • Automate post-incident hygiene where you can — e.g. a webhook or scheduled job that flags incidents missing service_name or resolution notes.

11. Quick reference checklist#11-quick-reference-checklist

  • Severities mapped to your SLAs; default severity set intentionally
  • Statuses reflect your real workflow (e.g. Declared → Mitigated → Resolved → Closed)
  • Commander and Investigator roles understood; assignment habit established
  • Declare-incident escalation step on critical, non-default routes
  • Slack app installed, users linked, auto-channel + announcements configured
  • Channel naming template and auto-archive (30–60 days) set
  • service_name + severity + team + environment labels applied consistently
  • Timeline discipline: notes, status updates, and emoji reactions used live
  • Resolution notes + attached alert groups + corrected labels on every resolve
  • Drills run regularly and excluded from production analytics
  • MTTR/MTTA and recurring-issue trends reviewed; learnings fed back
  • Incident config scripted via the Incident API; declare-triggers in Terraform
