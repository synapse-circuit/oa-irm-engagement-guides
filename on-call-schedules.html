On-Call Schedules

A practical guide to designing, operating, and scaling on-call schedules in Grafana Cloud IRM. Written for platform teams configuring schedules and for engineers who will be on-call.

1. Why on-call schedules matter#1-why-on-call-schedules-matter

On-call schedules determine who receives pages when escalation chains execute. Well-designed schedules ensure reliable coverage while respecting team members' time. In Grafana IRM, alerts flow through this path:

text
Alert → Route → Escalation Chain → Schedule → On-call Responder

Escalation chains reference schedules through notification steps ("Notify users from on-call schedule"), so schedule design and escalation design go hand in hand.

Key concept — dynamic evaluation

IRM evaluates schedules at *execution time*, not when the alert was created. If someone swaps a shift mid-escalation, the new on-call person receives the next notification. This differs from escalation chains, which are snapshotted when an alert group is created.

2. Core concepts#2-core-concepts

ConceptDefinition
ScheduleThe container that defines who is on-call at any given time; holds one or more shifts/rotations
RotationA recurring pattern (daily, weekly, custom) that generates on-call shifts
ShiftA specific time period when a person or group is responsible for responding
LayerConcurrent rotation patterns; shifts in higher layers override lower ones
OverrideA one-time exception for time off or special coverage; doesn't change the underlying rotation
Shift swapAn exchange of shifts between two users; maintains rotation continuity and is easier to audit
Recurrence groupA group of users on-call simultaneously within a rotation; all members are notified together

3. Choose the right schedule type#3-choose-the-right-schedule-type

Grafana IRM supports three management approaches:

TypeManaged viaBest forNotes
WebIRM UITeams new to on-call, simple rotations, visual editingDrag-and-drop editing, rotation preview, override management
iCalExternal calendar (e.g. Google Calendar)Migrations, teams with existing calendar-based schedulesChanges require editing the external calendar; IRM syncs periodically; limited in-app editing
API / TerraformCodeInfrastructure-as-code teams, automation, many teams at scaleFull API control; can enable web-based overrides on top of code-managed rotations
Rule of thumb

Web for simplicity, iCal for integration, API/Terraform for automation.

4. Rotation design best practices#4-rotation-design-best-practices

Pick a rotation length that matches your alert volume

PatternDurationUse case
Daily24 hoursHigh-frequency alerts, distributed teams
Weekly7 daysMost common; good work-life balance
Bi-weekly14 daysSmaller teams, less frequent alerts

Combine rotation frequency with shift length to fit your team: 12-hour shifts with a weekly rotation (two rotations covering day and night), business-hours shifts (9:00–18:00), or extended 36-hour shifts on a bi-daily rotation.

Set the rotation start explicitly

Don't rely on default behavior. Distinguish shift start (when the shift pattern begins each day/week) from rotation start (when the rotation through users begins) — set the rotation start deliberately when you want handoffs aligned to a specific date, such as a sprint boundary.

Use recurrence groups for shared responsibility

Group multiple users in one recurrence group to put them on-call simultaneously. Common patterns: co-primary responders, follow-the-sun (groups per time zone), graduated response (junior/senior pairing), shadow coverage for onboarding, and backup coverage during critical periods.

Layer schedules for escalation depth

Use separate schedules for primary, secondary, and management tiers, referenced from one escalation chain:

text
1. Notify on-call from "Primary Schedule"
2. Wait 5 minutes
3. Notify on-call from "Secondary Schedule"
4. Wait 10 minutes
5. Notify on-call from "Management Schedule"

Primary is the first line of defense (people most familiar with the system), secondary backs up if primary doesn't acknowledge in time, and tertiary is the final escalation point.

Common rotation patterns

Documented examples you can adapt (see schedule examples):

  1. Weekly rotation with 12-hour daily shifts (day/night split)
  2. Bi-daily rotation during workdays (weekday mask on)
  3. Bi-daily rotation with 36-hour shifts (weekday mask off)
  4. Weekly rotation with 9-hour workday shifts (9:00–18:00)
  5. Bi-weekly rotation with 8-hour daily shifts (repeat groups in the list to alternate every two weeks)
  6. Team rotation with multiple users per shift (e.g. Group 1: Alice + Bob → Group 2: Charlie → Group 3: Diana + Eve)

5. Time zones and distributed teams#5-time-zones-and-distributed-teams

  • Enable timezone support for new web schedules: shifts respect the schedule's timezone and daylight saving time is handled automatically. Legacy UTC-stored shifts require manual DST adjustment and cause cross-timezone confusion.
  • Test timezone changes carefully. A rotation starting "Monday 9am" in US/Pacific may fall on Monday or Tuesday in UTC depending on DST; changing a schedule's timezone can unexpectedly shift the rotation day.
  • For follow-the-sun coverage, create one rotation (or recurrence group) per region and verify handoff times land inside each region's working hours.

6. Handling changes: swaps, overrides, and priorities#6-handling-changes-swaps-overrides-and-priorities

  • Prefer shift swaps for planned changes. The swapped user returns to their normal position afterward, rotation continuity is maintained, and swaps are easier to track and audit.
  • Use overrides for last-minute coverage. Overrides create a one-time exception without altering the underlying rotation.
  • Set priorities intentionally. When shifts overlap, higher priority wins. Overrides typically use priority 99 (highest); primary shifts use lower priorities (0–10).
  • When editing rotations, choose Save as new (rather than Update) to preserve rotation history and version your rotations.

7. Monitor schedule quality#7-monitor-schedule-quality

Grafana IRM scores each schedule from 0–100:

ScoreRatingMeaning
81–100GreatWell-balanced, consistent coverage
61–80GoodMinor improvements possible
41–60MediumSome gaps or imbalances
21–40LowSignificant improvements needed
0–20PoorMajor coverage issues

Practices to keep quality high:

  • Enable gap and empty-shift reports. Gaps (periods with no coverage) and empty shifts (shifts with no assigned users) both cause missed alerts.
  • Review balance scores regularly to catch overloaded members; adjust rotations if some users consistently carry more load.
  • Account for holidays and time off when assessing fairness, and consider timezone distribution for follow-the-sun teams.
  • Note that deleted users or users lacking on-call permissions also lower the score.
  • Enable Slack notifications for weekly gap reports and shifts missing users.

8. Onboarding responders#8-onboarding-responders

  • Users need Admin or Editor roles to be assigned shifts; Viewer-role users cannot be on-call or receive alert notifications.
  • Every responder must configure personal notification rules (default and important chains) — a schedule is only as good as the notifications behind it.
  • Have responders install the Grafana IRM mobile app and connect Slack in their IRM profile (required for auto-updated Slack on-call user groups).
  • When testing a new schedule, add yourself as the current on-call user first to avoid paging teammates.
  • Verify with the Final schedule view and the On-call now indicator before wiring the schedule to production escalation chains.

9. Schedules as code (Terraform and API)#9-schedules-as-code-terraform-and-api

Managing schedules as code brings automation and efficiency, consistency across teams, version control and collaboration through Git, CI/CD integration, and confident scaling — replicate proven rotation patterns across dozens of teams.

Terraform

The Grafana Terraform provider manages schedules with these resources:

  • grafana_oncall_schedule — the schedule container (type = "calendar" for Terraform-defined shifts; enable_web_overrides = true lets responders manage overrides in the UI while code owns the rotations)
  • grafana_oncall_on_call_shift — the rotation pattern (type = "rolling_users" is the standard choice; recurrent_event is deprecated)
  • grafana_oncall_escalation — connects the schedule to an escalation chain
  • Data sources: grafana_oncall_user, grafana_oncall_team, grafana_oncall_slack_channel, grafana_oncall_user_group

Provider setup:

terraform
provider "grafana" {
  alias      = "oncall"
  url        = "<Stack-URL>"
  auth       = "<Service-account-token>"
  oncall_url = "<OnCall-URL>"
}

A complete weekly rotation:

terraform
data "grafana_oncall_user" "user_one" {
  provider = grafana.oncall
  username = "user_one"
}

data "grafana_oncall_user" "user_two" {
  provider = grafana.oncall
  username = "user_two"
}

resource "grafana_oncall_on_call_shift" "week_shift" {
  provider   = grafana.oncall
  name       = "Week shift"
  type       = "rolling_users"
  start      = "2025-03-01T00:00:00"
  duration   = 60 * 60 * 24  # 24 hours in seconds
  frequency  = "weekly"
  by_day     = ["MO", "TU", "WE", "TH", "FR", "SA", "SU"]
  week_start = "MO"
  rolling_users = [
    [data.grafana_oncall_user.user_one.id],
    [data.grafana_oncall_user.user_two.id]
  ]
  time_zone = "UTC"
}

resource "grafana_oncall_schedule" "primary" {
  provider  = grafana.oncall
  name      = "Primary"
  type      = "calendar"
  time_zone = "UTC"
  shifts    = [grafana_oncall_on_call_shift.week_shift.id]
}

resource "grafana_oncall_escalation" "notify_schedule" {
  provider                     = grafana.oncall
  escalation_chain_id          = grafana_oncall_escalation_chain.default.id
  type                         = "notify_on_call_from_schedule"
  notify_on_call_from_schedule = grafana_oncall_schedule.primary.id
  position                     = 0
}

Scaling tip: build rolling_users dynamically from a team map to stamp out consistent regional rotations:

terraform
resource "grafana_oncall_on_call_shift" "emea_weekday_shift" {
  name       = "EMEA Weekday Shift"
  type       = "rolling_users"
  start      = "2022-02-28T03:00:00"
  duration   = 60 * 60 * 12 # 12 hours
  frequency  = "weekly"
  interval   = 1
  by_day     = ["MO", "TU", "WE", "TH", "FR"]
  week_start = "MO"
  rolling_users = [for k in flatten([
    local.teams_map_of_user_id.emea,
  ]) : [k]]
  start_rotation_from_user_index = 0
  team_id = data.grafana_oncall_team.my_team.id
}

Key details to remember: duration is in seconds; start uses yyyy-MM-dd'T'HH:mm:ss; level sets shift priority; start_rotation_from_user_index controls who starts first; existing schedules can be imported with terraform import grafana_oncall_schedule.name "{{ id }}".

API

For custom integrations or dynamic management, use the IRM Schedules API:

bash
curl -X POST "https://<OnCall-API-URL>/api/v1/schedules/" \
  -H "Authorization: Bearer $GRAFANA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Primary On-Call Schedule",
    "team_id": "your-team-id",
    "type": "calendar",
    "time_zone": "UTC"
  }'

Endpoints: GET/POST /api/v1/schedules/, PUT/DELETE /api/v1/schedules/{schedule_id}.

As-code best practices

  • Use source control — store Terraform configurations and API scripts in Git to track changes
  • Automate deployments — use CI/CD (GitHub Actions, Terraform Cloud) to manage schedules across environments
  • Apply RBAC — restrict who can modify schedules via API tokens and IAM policies
  • Test before applying — always run terraform plan before deploying to production
  • Use variables and modules — create reusable schedule patterns and stamp them out per team
  • Document your approach — maintain documentation of schedule structure and rotation patterns
  • Implement monitoring — alert on schedule configuration changes or failures
  • Always specify time zones per rotation and test across DST boundaries for long-lived rotations

10. Quick reference checklist#10-quick-reference-checklist

  • Choose schedule type: web (simplicity), iCal (integration), API/Terraform (automation)
  • Match rotation length to alert volume (weekly is the most common default)
  • Set rotation start explicitly; align handoffs to working hours
  • Enable timezone support; verify DST behavior
  • Use recurrence groups for co-primary/shadow patterns
  • Build primary → secondary → management escalation tiers
  • Set override priority high (99); primary shifts low (0–10)
  • Prefer shift swaps for planned changes; overrides for last-minute cover
  • Enable quality reports; keep score above 80
  • Ensure all responders have Editor+ roles and notification rules configured
  • Manage at scale with Terraform modules + Git + CI/CD
