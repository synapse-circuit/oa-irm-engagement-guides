Insights

A practical guide to measuring and improving incident response with Grafana Cloud IRM Insights — alert group metrics, incident analytics, insight logs, and the improvement loops they enable. Part 4 of the IRM enablement series, following On-Call Schedules, Escalation Chains, and Integrations.

1. What IRM Insights is#1-what-irm-insights-is

IRM Insights is the analytics layer of Grafana IRM, found under Alerts & IRM → IRM → Insights. It has two halves:

  • Alert group insights and metrics — Prometheus-format metrics plus audit-style insight logs covering alert volume, response and resolution times, notification load per user, and configuration changes.
  • Incident insights — a pre-built dashboard plus a Grafana Incident data source for building custom dashboards over incident data: MTTR, MTTD, frequency, team impact, and label-based patterns.

Questions it answers: Where are our response bottlenecks? Which integrations are noisiest? Who is carrying too much on-call load? Are MTTR and MTTA trending the right way? Who changed IRM configuration and when?

Incident insights are included with all Grafana IRM plans at no additional cost.

2. The four alert group metrics#2-the-four-alert-group-metrics

IRM exports four Prometheus metrics. In Grafana Cloud they live in the preinstalled grafanacloud-usage data source (org-level — one data source serves all stacks, so filter by stack id or slug). Cloud metric prefix: grafanacloud_oncall_instance_; self-managed OSS prefix: oncall_.

MetricTypeWhat it measures
..._alert_groups_totalGaugeAlert groups per integration by state (firing, acknowledged, resolved, silenced)
..._alert_groups_response_time_secondsHistogramTime from alert group start to first action (MTTA proxy), rolling last 7 days
..._alert_groups_resolution_time_secondsHistogramTime from alert group start to resolution (MTTR proxy), rolling last 7 days
..._user_was_notified_of_alert_groups_totalCounterAlert groups each user was notified of (on-call load)

Labels: id/slug/org_id (stack), team, integration, service_name (from the alert group's service_name label — "No service" if absent), state (on the gauge), username (on the notification counter). Histogram buckets: 60, 300, 600, 3600, +Inf seconds.

Example queries from the docs:

promql
# Firing alert groups for one integration
grafanacloud_oncall_instance_alert_groups_total{integration="Grafana Alerting", state="firing"}

# Alert groups responded to within 10 minutes
grafanacloud_oncall_instance_alert_groups_response_time_seconds_bucket{integration="Grafana Alerting", le="600"}

# Per-user notification load
sum by (username) (grafanacloud_oncall_instance_user_was_notified_of_alert_groups_total)

# Notification rate for one service
rate(grafanacloud_oncall_instance_user_was_notified_of_alert_groups_total{service_name="auth"}[5m])

Note: incident data is *not* exported as Prometheus metrics — query it through the Grafana Incident data source (section 4).

3. The pre-built dashboards#3-the-pre-built-dashboards

Alert Groups Insights dashboard

(IRM plugin): find it in the dashboards list under folder General, tag irm. Select grafanacloud_usage as the data source; filter by stack, team, and integration.

Two operational cautions:

  • Plugin updates and re-imports reset customizations. Preserve changes with Save As — or better, export the JSON and manage your copy as code (section 7).
  • Re-import when needed via Administration → Plugins → IRM → Dashboards → Re-import.
Incident Insights dashboard

first-time setup via IRM → Insights → Incidents tab → "Set up Insights dashboard". Setup auto-configures the Grafana Incident data source and creates a service account with a viewer token, then builds the dashboard.

Core incident metrics:

  • MTTR = incidentEnd − incidentStart (falls back to closedTime if end unset)
  • MTTD = incidentCreated − incidentStart (exposed as time_to_discovery)
  • Frequency, team impact, root-cause patterns via labels, time-of-day patterns

Timestamps incidentStart and incidentEnd are editable — even after resolution — and MTTR/MTTD recalculate automatically. Correct your timelines in the post-incident review and your analytics stay honest. Insights queries ignore Drill (practice) incidents unless you explicitly query isdrill:true.

4. Custom dashboards#4-custom-dashboards

On alert group metrics

any panel against the grafanacloud-usage data source using the PromQL above. Useful panels: noisy-integration ranking (sum by (integration) (alert_groups_total{state="firing"})), per-service response-time heatmap, per-user notification load.

On incident data

create panels against the Grafana Incident data source using incident query syntax. Dashboard template variables must use these reserved, case-sensitive names: statuses (Status query type), severities (Severity), labels (Label), roles (Role). Combined example:

text
or(status:$statuses) or(severity:$severities) or(label:$labels)

Filter logic gotcha: multiple label: filters combine with AND; other filters like status: combine with OR.

Docs-recommended practices: start with the pre-built dashboards, create custom dashboards per team or service, use consistent labeling, track trends over time rather than point-in-time values, and read MTTR alongside incident count (a falling MTTR with rising count is not a win).

5. Meta-monitoring: alert on your alerting#5-meta-monitoring-alert-on-your-alerting

Insights metrics are ordinary Prometheus series — alert on them like anything else (Admin or Editor role required):

  • Notification failures (Grafana Alerting side): grafanacloud_grafana_instance_alerting_notifications_failed_total:rate5m (labeled by integration).
  • Silence-means-trouble detection: enable per-integration heartbeat monitoring (timeout 1 minute – 24 hours, set longer than the monitoring interval) — covered in the Integrations guide.
  • On-call coverage: enable schedule gap and empty-shift reports; schedule quality metrics (coverage percentage, balance score, overloaded users) are in-product only, not exported.
  • Response degradation: alert when the share of alert groups responded to within 10 minutes (le="600" bucket over _count) drops below your target.
  • Alert state history is queryable in Loki: data source grafanacloud-<stack>-alert-state-history, query {from="state-history"} | json.

6. Insight logs: the audit trail#6-insight-logs-the-audit-trail

Alert group insight logs record configuration changes and system events. In Grafana Cloud they're auto-provisioned in the Usage Insights Loki data source (grafanacloud-<YOUR-STACK-NAME>-usage-insights); storage and queries don't count against your Loki costs.

Base query:

logql
{instance_type="oncall"} | logfmt | __error__=``

Three log types via the action_type label:

  1. resource — created/updated/deleted for IRM resources (integrations, escalation chains and policies, schedules and shifts, webhooks, API tokens, users…), with author, resource_type, and JSON prev_state/new_state.
  2. maintenance — maintenance started/finished per integration, with the mode used.
  3. chat_ops — Slack/Teams/Telegram/mobile-app connection changes.

Examples from the docs:

logql
# Everything one user changed
{instance_type="oncall"} | logfmt | __error__=`` | action_type = `resource` and author="username"

# All schedule changes
{instance_type="oncall"} | logfmt | __error__=`` | action_type = `resource` and (resource_type=`web_schedule` or resource_type=`calendar_schedule` or resource_type=`ical_schedule`)

# Maintenance history for an integration
{instance_type="oncall"} | logfmt | __error__=`` | action_type = `maintenance` and resource_id=`INTEGRATION_ID`

Resource IDs are visible in IRM URLs (e.g. .../integrations/C5VXMIFKKP67K). Use insight logs to answer "who changed this escalation chain before the missed page?" — and pair them with as-code management so the same question is also answerable from Git history.

7. The improvement loops#7-the-improvement-loops

Insights only pay off when wired into recurring practices:

On-call load balancing (weekly/monthly).

Review sum by (username) notification load and schedule balance scores; rebalance rotations for overloaded members; account for holidays and follow-the-sun distribution.

Noise reduction (monthly).

Rank integrations by firing alert groups; fix grouping keys and thresholds on the top offenders; add volume-throttling escalation steps (e.g. only page when >5 alerts in 30 minutes); verify maintenance mode is used for planned work.

Response tuning (monthly/quarterly).

Watch time to first acknowledgment, escalation depth, and false escalations — slow acknowledgment argues for earlier important-notification steps; deep escalations argue for shorter waits or more channels; false escalations argue for alert-quality work or throttling.

Post-incident hygiene (every incident).

Finalize the timeline (edit incidentStart/incidentEnd so MTTR/MTTD are accurate), add resolution notes, attach related alert groups (max 5 per incident), and correct labels — analytics are only as good as this discipline.

Labeling for analytics (ongoing).

Labels serve routing, triage, *and* analytics. A minimal effective set is 4–5 labels — Grafana Engineering uses namespace, severity, service_name, cluster. service_name is the key that ties alert rules → alert groups → incidents → SLOs together in the Service Center. Limits: 50 labels per alert group (first 50 alphabetically win), and labels are immutable once assigned to an alert group.

8. Insights as code (Terraform and API)#8-insights-as-code-terraform-and-api

Insights itself is mostly read-side, but everything that *feeds* it — and everything you build *on* it — can be managed as code:

Dashboards as code.

Export the pre-built Alert Groups Insights dashboard JSON (Save As → export) and provision your customized copy with the standard grafana_dashboard resource. This also solves the plugin-update-resets-customizations problem permanently:

terraform
resource "grafana_dashboard" "irm_insights_custom" {
  folder      = grafana_folder.observability.id
  config_json = file("${path.module}/dashboards/irm-insights-custom.json")
}
Meta-monitoring alerts as code.

Provision alert rules on the IRM metrics with grafana_rule_group, pointing at the grafanacloud-usage data source — e.g. a rule on per-user notification load or on the le="600" response-time bucket share.

Labels as code.

Attach analytics labels to integrations in Terraform so service_name and friends flow into every metric:

terraform
data "grafana_oncall_label" "service_payments" {
  key   = "service_name"
  value = "payments"
}

resource "grafana_oncall_integration" "payments" {
  name    = "Payments Alertmanager"
  type    = "alertmanager"
  labels  = [data.grafana_oncall_label.service_payments]
  default_route {
    escalation_chain_id = grafana_oncall_escalation_chain.default.id
  }
}

(Dynamic labels are UI/API only.)

Provider setup

is the same as the rest of the series: Grafana provider >= 3.0.0 with the oncall alias. Incident resources are managed via the separate Incident API, not the OnCall API; ChatOps configs and admin settings are not IaC-manageable. Note that IRM user IDs differ from Grafana user IDs — map via data "grafana_oncall_user".

As-code best practices

keep dashboards, alert rules, labels, and the IRM resources they measure in one workspace; PR review plus terraform plan in CI; service-account tokens with least privilege (viewer for dashboard data sources); and treat the insight-log audit trail and Git history as complementary records of change.

9. Service Center and SLOs#9-service-center-and-slos

The service_name label is the connective tissue: it flows from alert rule → alert instance → alert group → incident, appears on all four IRM metrics, and powers the Service Center — a per-service view unifying health, SLOs, alerts, incidents, on-call, and synthetic checks. Uses: on-call handoffs (what's hot on my services?), operational reviews, SLO correlation (filter SLO dashboards by incidents sharing service_name), and dependency awareness. Label consistently and per-service insights come free.

10. Quick reference checklist#10-quick-reference-checklist

  • Pre-built Alert Groups Insights dashboard imported; data source set to grafanacloud_usage
  • Incident Insights dashboard set up via the Incidents tab
  • Customized dashboards saved-as / exported and provisioned as code
  • service_name + severity labels applied consistently (4–5 analytics labels total)
  • Meta-monitoring alerts: notification failures, response-time degradation, heartbeats
  • Schedule gap/empty-shift reports enabled; balance reviewed monthly
  • Noisy-integration review monthly; grouping and throttling fixes tracked
  • Post-incident: timelines corrected, notes added, alert groups attached, labels fixed
  • Insight logs used for config-change audits; as-code for the same in Git
  • Trends reviewed over time — MTTR alongside incident count, never alone
