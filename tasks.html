Tasks

A practical guide to coordinating action items during and after an incident with Grafana Cloud IRM Tasks — creation, ownership, status tracking, GitHub/Jira follow-through, and the API. Part of the IRM enablement series, closely tied to Incident Management.

1. What Tasks are#1-what-tasks-are

Tasks are Grafana IRM's built-in action-item tracker for incidents. They help you organize, assign, and track the specific steps needed to resolve an incident, so responders can be sure nothing falls through the cracks. Each task has a short description, a single assignee, and a status.

They live in the Tasks section of the right-hand sidebar on the incident details page, and can be created and managed from within the incident's Slack channel. Alongside the timeline, tasks form the permanent record of what was done during an incident — and the mechanism for carrying remediation work forward afterward.

Use tasks to track remediation steps, assign responsibility, monitor progress, and record the actions taken. Converting tasks to GitHub or Jira issues carries the durable follow-up work into your engineering backlog.

2. Creating tasks#2-creating-tasks

There are several entry points, so you can capture an action item wherever the conversation is happening:

  • Tasks sidebar — type an action-oriented description in the Tasks field and click +Task.
  • Slack slash command — /grafana incident tasks add <task>, or assign at creation with /grafana incident tasks add <task> @user.
  • Slack action button — type /grafana in the incident channel and click Add task.
  • 💡 bulb emoji — react to any message in the incident Slack channel with 💡 (:bulb:) to turn it into a task (a post-incident-review action item) without leaving the conversation.
  • Paste a GitHub issue URL — paste an issue link into the Tasks field and click +Task; it appears as a task with its status synced from GitHub.

A task carries a description (text), an optional single assignee, and a status. There is no separate due-date or priority field, so keep the description specific and self-contained.

3. Statuses, assignment, and lifecycle#3-statuses-assignment-and-lifecycle

Tasks move through three statuses. Click the status icon to cycle it forward:

StatusIconMeaning
Todo☐Created, but work hasn't started
In Progress🕜Work has begun but isn't complete
Done✔️Completed

The icon cycles Todo → In Progress → Done → Todo. Assign a task by clicking the + people icon and selecting a user; reassign or unassign by clicking the current assignee. Every task has exactly one assignee — that single-owner model is deliberate and worth preserving.

Some tasks are system-created (for example, role-assignment tasks) and are marked immutable — they can't be edited or reassigned.

4. GitHub and Jira follow-through#4-github-and-jira-follow-through

An incident ends, but the remediation work often doesn't. Converting tasks to issues moves that work into the tools your engineers already live in, and keeps it alive after the incident channel is archived.

GitHub Issues.

From a task's menu (⋯), choose Convert to GitHub Issue, enter organization/repository, add a description, and confirm — the task now links to the issue and shows its live GitHub status. You can also Link to an existing issue, or create a task by pasting an issue URL. Unlinking only removes the issue from the incident's task list; it never modifies or deletes the GitHub issue itself. Setup needs the IRM Admin role plus GitHub admin rights to install the Grafana IRM GitHub app and pick which repositories to connect.

Jira.

From a task's menu, Convert to Jira Issue (or Link to an existing one). Jira status syncs with the issue, and the Jira integration can auto-create an issue when an incident is declared and update its status as the incident progresses. Two constraints to know: it's Jira Cloud only, and IRM sends only four fields on creation — Summary, Description, Project, and Issue Type — so issue creation will fail if your Jira project requires other mandatory fields. Trim those required fields or pre-fill them in Jira.

5. Capturing action items in the moment#5-capturing-action-items-in-the-moment

The best incident notes are the ones you don't have to reconstruct afterward. During the incident:

  • Use the 💡 reaction in Slack to capture decisions and follow-ups as tasks the instant they're mentioned — no app switching, no "we'll write it down later."
  • Assign an owner at creation (/grafana incident tasks add "deploy hotfix" @bob) so accountability is set immediately.
  • Keep the incident commander's view current by updating statuses as work progresses — status is how the whole room reads overall progress.
  • Use /grafana incident tasks list to review the open task list at any point, especially before moving to resolve the incident.

6. Post-incident follow-through#6-post-incident-follow-through

Tasks bridge the live incident and the retrospective. Action items captured with 💡 become the raw material of the post-incident review. Before you resolve an incident, review the task list so nothing open is silently lost when the channel archives (the incident Slack channel auto-archives after a configurable window — commonly 30–60 days — with a 24-hour warning). For anything that outlives the incident, convert it to a GitHub or Jira issue so it lands in a durable backlog rather than a channel that will disappear.

7. Best practices#7-best-practices

  • Write clear, actionable descriptions. "Restart the database cluster in us-west" beats "Fix database." A task should read like a checklist item someone can pick up cold.
  • Assign a single owner. One assignee per task is the model — use it to make accountability unambiguous. Shared ownership is no ownership.
  • Update statuses in real time. The commander and the room read progress from task status; stale statuses hide risk.
  • Capture in the moment. Use 💡 in Slack to log action items as they're discussed, not after.
  • Keep tasks atomic. Break multi-step work into separate tasks rather than one sprawling item.
  • Review before resolving. Walk the open task list before closing the incident; nothing important should be left in Todo.
  • Push durable work to an issue tracker. Convert follow-ups to GitHub/Jira so they survive channel archival and enter the normal engineering workflow.

8. Roles and permissions#8-roles-and-permissions

Tasks use basic-role authorization, not RBAC — the same as the rest of incident management. Creating, editing, and assigning tasks requires the Editor or Admin basic role; Viewers have read-only access. Setting up the GitHub or Jira integrations additionally requires the IRM Admin role plus admin rights in the respective external tool. RBAC roles don't change task permissions, so plan access at the basic-role level for responders who need to manage tasks.

9. Tasks as code (the Incident API)#9-tasks-as-code-the-incident-api

There is no Terraform resource for incident tasks — incidents and their tasks are managed only through the Incident API. That said, tasks are fully scriptable, which is useful for automations like seeding a standard checklist of tasks onto every incident of a given type.

The Incident API is JSON-over-HTTP RPC: every call is an HTTP POST to {base}/{Service}.{Method}.

  • Base: https://your-stack.grafana.net/api/plugins/grafana-irm-app/resources/api/v1
  • Auth: Authorization: Bearer glsa_... (a Grafana service account token)
  • Content-Type: application/json; charset=utf-8

TasksService exposes five methods:

MethodKey fieldsPurpose
AddTaskincidentID, text, assignToUserIDCreate a task
UpdateTaskStatusincidentID, taskID, status (todo/progress/done)Move a task's status
UpdateTaskTextincidentID, taskID, textEdit the description
UpdateTaskUserincidentID, taskID, userIDReassign the task
DeleteTaskincidentID, taskIDRemove the task

Note the surface: assignment is UpdateTaskUser (there is no AssignTask), removal is DeleteTask, and there's no standalone task-query RPC — tasks come back embedded in each response's taskList (which also carries todoCount and doneCount) and via incident queries.

Create a task:

bash
curl "https://your-stack.grafana.net/api/plugins/grafana-irm-app/resources/api/v1/TasksService.AddTask" \
  --request POST \
  --header 'Content-Type: application/json; charset=utf-8' \
  --header 'Authorization: Bearer glsa_...' \
  --data '{
    "incidentID": "incident-123",
    "text": "Restart database cluster in us-west region",
    "assignToUserID": "user-456"
  }'

Move it to done:

bash
curl "https://your-stack.grafana.net/api/plugins/grafana-irm-app/resources/api/v1/TasksService.UpdateTaskStatus" \
  --request POST \
  --header 'Content-Type: application/json; charset=utf-8' \
  --header 'Authorization: Bearer glsa_...' \
  --data '{"incidentID":"incident-123","taskID":"task-789","status":"done"}'

An official Go client (github.com/grafana/incident-go) is available, and outgoing webhooks emit task activity kinds — taskAdded, taskUpdated, taskCompleted, taskDeleted — which you can use to mirror tasks into external systems.

As-code best practices

  • Seed standard checklists. Script AddTask calls to stamp a consistent set of action items onto incidents of a given type or severity (e.g. "post status page update", "notify account team").
  • Mirror with webhooks. Use the task* activity kinds to sync tasks outward to a system of record if you need one beyond GitHub/Jira.
  • Least-privilege tokens. Use a scoped service account token for task automation, and keep the automation code in Git with review.

10. Quick reference checklist#10-quick-reference-checklist

  • Responders who manage tasks have Editor or Admin basic roles
  • GitHub and/or Jira integration installed (Admin role) if you want follow-through sync
  • Team knows the 💡 Slack reaction captures a task in the moment
  • Task descriptions are specific and actionable
  • Every task has a single owner assigned
  • Statuses updated in real time during the incident
  • Open task list reviewed before resolving the incident
  • Durable follow-ups converted to GitHub/Jira issues before channel archival
  • Standard task checklists seeded via the API for recurring incident types (optional)
