Settings

A practical guide to administering Grafana Cloud IRM — access and roles, API tokens, ChatOps, org-level behavior toggles, and incident-response configuration — and to managing as much of it as code as the platform allows. Written for the platform admins who own an IRM stack. Part of the IRM enablement series.

1. What the Settings section is#1-what-the-settings-section-is

The IRM Settings area is the administration hub for an IRM stack, at Alerts & IRM → IRM → Settings. It's a tabbed page with three documented tabs:

  • Admin & API — org-wide behavior toggles, API token management, and the IRM API base URLs.
  • Incidents — the configurable incident-response workflow: severities, statuses, roles, custom fields, and channel prefixes.
  • Team Access Management — per-team visibility and the default team.

One scoping subtlety worth knowing up front: not everything an admin configures lives under the Settings tab. Several org-level behaviors sit under IRM → Integrations → Apps → Slack (incident channel creation, auto-archive, acknowledge reminders), and connecting a chat workspace is done through the Grafana Cloud portal. So "Settings" in the strict sense is those three tabs; "settings" in the everyday admin sense spans those plus the Slack app config and ChatOps connection. This guide covers the whole administrative surface.

2. Access management: roles#2-access-management-roles

Access is layered: basic roles (inherited from Grafana) plus IRM RBAC roles (fine-grained, and they don't change the basic role).

Basic roles:

RoleIRM access
ViewerRead-only across IRM
EditorEdit most resources (schedules, alert groups); cannot create integrations, escalation chains, or outgoing webhooks
AdminFull access to all IRM features and settings
NoneNo default access; grant access with an IRM RBAC role
Key IRM RBAC roles

(assigning any of them also grants IRM plugin access):

  • OnCaller — read all IRM plus edit alert groups, schedules, and own settings. The role for on-call responders.
  • Notifications Receiver — receive alert notifications and edit own IRM user settings; the minimal responder grant.
  • Incident Access — plugin access for incident workflows only, no OnCall permissions.
  • Reader / Editor / Admin — map to the basic roles.
  • Specialized reader/editor roles for each resource type: Integrations, Escalation Chains, Schedules, ChatOps, Outgoing Webhooks, Maintenance, API Keys, Notification Settings, User Settings (Reader/Editor/Admin), and org Settings (Reader/Editor).

Permission strings are prefixed grafana-irm-app. — e.g. grafana-irm-app.schedules:write, grafana-irm-app.other-settings:write, grafana-irm-app.api-keys:write.

Assign roles

as an org admin: Administration → Users and access → Users → select the user → Role picker → under Grafana IRM pick the role → Apply. Roles can also be assigned to teams and via the API/Terraform.

Features that don't support RBAC.

Incidents, Tasks, and Incident settings still use basic-role authorization only — RBAC roles don't affect them. Plan for this: managing incident configuration requires the Admin basic role, regardless of RBAC.

3. Teams: scoping resources#3-teams-scoping-resources

IRM teams sync from Grafana teams (Administration → Teams) roughly every four hours, and immediately when you open or refresh any IRM page. Set team visibility under Settings → Team Access Management — either all Grafana users can see the team's resources, or only team members and admins. Admins see all teams; Editors and Viewers see only teams they belong to (unless visibility is "all users"). Cross-team resources appear to non-members as 🔒 Private resource. Note that to *manage* a team's resources in IRM you must be a member of that team — even admins add themselves temporarily.

RBAC decides *what actions* a user can take; team membership decides *which resources* they act on. Combine the two for clean scoping.

4. API and tokens#4-api-and-tokens

API access is configured at Settings → Admin & API, which shows the auto-provisioned IRM API base URLs and an API Tokens section (Create New Token → name + permissions; the token is shown once and can't be retrieved later).

There are two auth methods for the OnCall API:

  • Grafana Cloud service account token (recommended) — granular, rotatable, centrally managed. Send Authorization: Bearer <token> and X-Grafana-URL: https://your-stack.grafana.net.
  • Legacy OnCall API key — user-specific; send Authorization: <key> (no Bearer, no X-Grafana-URL). Only the creating user can see or manage it.

Service-account token limitations to know: they can't retrieve the caller's own user profile, can't perform state-changing alert-group actions (acknowledge/resolve/silence — use a user token or the UI), and /info, /make_call, /send_sms still require a legacy key. A 500 usually means the endpoint doesn't accept service-account auth or the token lacks permissions.

The API is rate-limited to 300 requests per API key per minute; over-limit calls return HTTP 429.

Token best practices

prefer service-account tokens over personal/legacy keys; grant only the permissions each token needs; store tokens in a secrets manager or Terraform variables, never in source control; rotate them on a schedule; and hand out the API Keys Editor role sparingly, since it also confers the ability to use the API.

5. Org-level behavior toggles (Admin & API)#5-org-level-behavior-toggles-admin-api

These toggles change how the whole stack behaves — set them deliberately and document why:

  • Notification channel visibility — show/hide channels (Slack, Teams, …) in users' personal notification rules. On by default when an integration is installed. Hiding a channel only removes it from user profiles; it does not disable the integration itself.
  • Manually manage direct paging integrations (manually_manage_direct_paging_integrations) — turn on to stop IRM auto-creating per-team direct-paging integrations so you can manage them as code. Existing integrations are kept. Required before managing direct_paging integrations in Terraform.
  • Prefer important notification policy — direct pages via Slack use the recipient's *important* personal policy rather than default.
  • Require resolution notes (is_resolution_note_required) — responders must add a resolution note before resolving an alert group. Enforced in the UI, Slack, and bulk resolve — but not by the public API resolve endpoint.
  • Require team membership for updates — restrict write operations to members of the resource's team, across UI, mobile, Slack, Teams, and API. Bypassed by Admin/IRM-Admin, service accounts, and a user notified for a specific alert group (scoped to that one group). Read access is unaffected.
  • Disable schedule updates in the past — enforce future-only editing of web schedules (no past-dated overrides/swaps; rotation edits only via "Save as new"). Doesn't apply to Terraform/API schedules — use the until parameter there instead.

Admins also manage users' linked Slack profiles from IRM → Users (auto-synced when Grafana and Slack emails match).

6. ChatOps configuration#6-chatops-configuration

Chat integrations include Slack, Microsoft Teams, and Telegram. A few placement facts save confusion:

  • Workspace connection is done in the Grafana Cloud portal, not the Settings tab — install the Grafana Cloud app for Slack, then each user links their account under Profile → IRM tab → Slack connection.
  • One Slack workspace can serve multiple stacks, but you can't connect multiple workspaces to a single stack.
  • Org-level Slack behavior lives under IRM → Integrations → Apps → Slack: incident channel auto-creation, invite-on-create, auto-archive (30–60 days recommended, with a 24-hour warning), the channel name template (default {{ prefix }}-{{ date }}-{{ title }}), acknowledge-reminder and auto-unacknowledge timeouts, and rich link previews. These appear only when Slack is installed.

Updating ChatOps settings requires the IRM Admin RBAC role (or the ChatOps Editor role); Editor RBAC explicitly can't change them.

7. Incident-response settings (Incidents tab)#7-incident-response-settings-incidents-tab

Configured at Settings → Incidents — and because incident features are basic-role only, this needs the Admin basic role.

  • Severities — defaults Critical, Major, Minor, Pending; new incidents default to Pending (configurable). Custom severities have a Label and a numeric Level that is immutable after creation; map custom levels to the defaults (P1→Critical, etc.).
  • Statuses — defaults Active and Resolved; add custom statuses with name, icon, and color; reorder by drag.
  • Roles — defaults Commander and Investigator; add custom roles and flag the critical ones as key roles.
  • Custom fields — Text, Number, Single-select, Multi-select; mark a field Mandatory only when it truly must be completed before resolution.
  • Prefixes, announcements, and briefings — channel prefixes on the Incidents tab; announcements and briefings under customize-incident-response.

Keep the incident workflow small and meaningful: a handful of clear severities, statuses that mirror your real process, and mandatory fields reserved for the few that matter.

8. Who can change settings#8-who-can-change-settings

  • Incidents tab — Admin basic role (no RBAC path).
  • Admin & API / org settings — IRM Admin RBAC or Admin basic role; fine-grained equivalents are Settings Editor (other-settings:write), ChatOps Editor, API Keys Editor, and User Settings Admin. Editor RBAC cannot change admin settings, ChatOps, or other users' settings.
  • Team Access Management — admins manage all teams, but must be a member of a team to manage its resources.
  • Assigning any role requires Organization Administrator access.

9. Settings as code#9-settings-as-code

The honest picture of what's codifiable:

Terraform / OnCall API (grafana_oncall_*): integrations (including direct_paging once the manual-management toggle is on), escalation chains and steps, routes, schedules and shifts, shift swaps, outgoing webhooks, personal notification rules, and resolution notes. Provider setup uses the grafana/grafana provider (≥ 3.0.0) with an aliased oncall block; look up users with the grafana_oncall_user data source since IRM uses internal user IDs.

Read-only via API

users, teams, and organizations (synced from Grafana — reference teams by ID, don't create them here).

Incident API (separate)

incident resources and incident configuration.

UI-only

ChatOps configuration (Slack/Teams/Telegram) and admin org settings. These can't be Terraformed today, so capture them in written runbooks instead.

Service accounts and tokens, and RBAC role assignments, are managed with the broader Grafana provider — typically grafana_service_account, grafana_service_account_token, and role-assignment resources (confirm exact names against the current provider registry). The IRM docs themselves point to the UI flow (Admin & API → Create New Token) for token creation.

terraform
# OnCall provider setup (auth prerequisite for managing IRM as code)
provider "grafana" {
  alias               = "oncall"
  url                 = "https://your-stack.grafana.net"
  auth                = var.grafana_sa_token
  oncall_access_token = var.oncall_token
}

# A least-privilege service account + token for IRM automation
resource "grafana_service_account" "irm_ci" {
  name = "irm-terraform"
  role = "Editor"
}

resource "grafana_service_account_token" "irm_ci" {
  name               = "irm-terraform-token"
  service_account_id = grafana_service_account.irm_ci.id
}

As-code best practices

  • Version everything codifiable in Git with PR review; keep a separate Terraform workspace per environment (dev/staging/prod) and a remote state backend.
  • Document the UI-only settings (ChatOps, admin toggles, incident workflow) in a runbook so the full configuration is reproducible even where Terraform can't reach.
  • Store tokens securely (secrets manager / TF variables), rotate them, and scope service accounts to least privilege.
  • Validate in CI (terraform validate / plan on every PR) and apply after approval.

10. Quick reference checklist#10-quick-reference-checklist

  • Responders assigned OnCaller (or Notifications Receiver); Admin reserved for settings owners
  • User roles reviewed/audited against current responsibilities
  • Team visibility set intentionally; "Require team membership for updates" considered
  • Service-account tokens used (not personal keys), scoped, stored securely, rotated
  • Org toggles set deliberately: resolution notes, direct-paging management, schedule-past edits
  • ChatOps connected; Slack app behavior (auto-archive, naming, reminders) configured
  • Incident workflow configured: severities mapped, statuses match process, mandatory fields minimal
  • Codifiable resources managed in Terraform with PR review + per-env workspaces
  • UI-only settings captured in a runbook for reproducibility
