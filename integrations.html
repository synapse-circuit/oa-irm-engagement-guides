Integrations

A practical guide to connecting alert sources to Grafana Cloud IRM and shaping alerts with templates, grouping, and routing. Written for platform teams configuring integrations and for engineers who consume the resulting alerts. Companion to the On-Call Schedules and Escalation Chains guides.

1. What integrations are#1-what-integrations-are

Integrations are the entry points for alerts into Grafana IRM. Each integration is a unique HTTP endpoint that receives payloads from a monitoring system, plus the configuration that shapes those payloads into actionable alert groups.

Every payload follows a fixed lifecycle:

text
Payload arrives → Templates format it → Routes select a chain → Grouping ID evaluated → Alert group → Escalation chain runs

Four principles govern this pipeline:

  1. Routing happens before grouping.
  2. Each integration has its own routing and grouping configuration — settings never apply across integrations.
  3. Alerts on different routes never group together, even with identical grouping IDs.
  4. Each payload is an independent event — IRM never updates past payloads.

Think of routing as two stages: *source routing* (Grafana Alerting notification policies or Alertmanager routes deliver alerts to the right team's integration — coarse-grained) and *IRM routing* (routes inside the integration select escalation chains by severity or service — fine-grained).

2. Available alert sources and how they connect#2-available-alert-sources-and-how-they-connect

Built-in alert source integrations include Grafana Alerting, Alertmanager/Prometheus (also Mimir/Cortex), Amazon SNS (the path for CloudWatch), Datadog, Zabbix, New Relic, Sentry, Pingdom, PRTG, ElastAlert, Kapacitor, AppDynamics, UptimeRobot, Stackdriver (Google Cloud Monitoring), Inbound Email, Jira, ServiceNow, Zendesk — plus generic Webhook and Formatted Webhook integrations for anything else.

Nearly all connect the same way: IRM generates a unique endpoint URL with an embedded token, and you paste it into the source tool's webhook or notification configuration. Source-specific notes:

  • Grafana Alerting (same stack): use "Quick connect" on the integration tile — it creates the integration and a matching contact point; you still need to attach that contact point to a notification policy or alert rule. For an external Grafana instance, use the Alertmanager integration type instead.
  • Alertmanager/Prometheus: add a webhook_configs receiver with the integration URL (trailing slash required), send_resolved: true (enables auto-resolution), and max_alerts: 100 or lower to avoid oversized requests.
  • CloudWatch: alarm → SNS topic → HTTPS subscription pointing at the IRM Amazon SNS integration URL.
  • Inbound Email: IRM provisions a dedicated email address; alerts group by subject and auto-resolve when the body equals "OK".
  • Formatted Webhook: parses recognized fields — alert_uid (grouping), title, state (ok/alerting, drives auto-resolution), message, image_url, link_to_upstream_details. None are required, but including them improves handling. The plain Webhook type ingests any raw JSON as-is.

3. Integration topology: one per team#3-integration-topology-one-per-team

The single highest-leverage design decision: create one integration per team, and configure source-side label selectors so each team's integration receives only its own alerts. This keeps routing manageable, makes ownership unambiguous, and lets each team tune templates and grouping independently.

Also:

  • Assign every integration to a team for ownership and visibility.
  • Use purpose-revealing names ("Payments Alertmanager", "MyService heartbeat").
  • Maintain records of webhook sources and configurations — an integration inventory pays for itself during incidents.

4. Secure the endpoints#4-secure-the-endpoints

By default, any request to an integration URL is accepted — the URL's embedded token is the only protection. For sensitive environments, enable "Require a Grafana service account token to send alerts to this integration" in the integration settings. Requests must then carry Authorization: Bearer glsa_... from a service account with the grafana-irm-app.alert-groups:write permission; anything else gets 403 Forbidden.

Notes: bearer-token protection isn't available for Inbound Email or Amazon SNS (they can't attach headers). For Grafana Alerting contact points, add the token in the Authentication Header fields.

5. Alert templates (Jinja2)#5-alert-templates-jinja2

Templates transform raw JSON payloads into readable, actionable alerts. Three families:

  • Routing templates — must evaluate to True for a route to match, e.g. {{ "database" in payload.title | lower }}.
  • Appearance templates — per channel (Web, Slack, MS Teams, Telegram, SMS, phone call, email, mobile app): title, message, image URL.
  • Behavioral templates — grouping ID, auto-resolution signal, auto-acknowledge, source link.

Templates reference payload (raw alert data) and labels. Every integration ships with sensible defaults per source — customize only where it adds value.

Template design practices:

  • Add context responders act on: dashboard links, runbook URLs, service and instance labels, current values.
  • Use conditional formatting by severity so critical alerts look critical.
  • Keep SMS and phone-call titles concise — they're read aloud or truncated.
  • Test with real data: the template editor shows example payload, editor, and rendered result side by side; load a recent alert group or paste a custom payload.

Example message template (from the docs):

jinja2
{% set severity = payload.labels.severity | default('unknown') %}

**{{ payload.alertname }}**
{% if severity == 'critical' %}🔴 CRITICAL{% elif severity == 'warning' %}🟠 WARNING{% else %}ℹ️ INFO{% endif %}

**Details:**
- Service: {{ payload.labels.service | default('N/A') }}
- Instance: {{ payload.labels.instance | default('N/A') }}
- Value: {{ payload.value | default('N/A') }} {{ payload.unit | default('') }}

**Runbook:** {{ payload.annotations.runbook_url | default('No runbook available') }}

**Dashboard:** {{ payload.generatorURL | default('N/A') }}

6. Alert grouping: the noise killer#6-alert-grouping-the-noise-killer

The difference between good and poor grouping can mean receiving 1 phone call instead of 10 at 4am.

Two payloads join the same alert group when they render the same Grouping ID, arrive on the same route, and an *open* group (Firing, Acknowledged, or Silenced) with that ID exists. Resolved groups are closed — a matching new payload starts a new group.

  • Alertmanager and Grafana Alerting: keep the default {{ payload.groupKey }} template, and configure grouping at the source (notification policies — commonly alertname + grafana_folder, or alertname + namespace + cluster). Changing it breaks auto-resolution.
  • Other sources: compose a stable key, e.g. {{ payload.alertname }}:{{ payload.labels.service }}, or reuse native IDs (Datadog monitor ID, incident keys).
  • Good identifiers: alertname, service_name, namespace, groupKey. Never group on status fields (Firing/Resolved/OK) — fire and resolve events land in different groups and auto-resolution breaks. Avoid timestamps and unique per-event IDs (every alert becomes its own group).
  • Enable auto-resolution (allow_source_based_resolving) for sources that send resolve signals; pair with send_resolved: true on the source.
  • Notification templates render against a single payload of the group, so add differentiating context to the message template if grouped alerts look identical.
  • Prefer time-limited silences; review any "Silence forever" groups periodically — without auto-resolution they absorb alerts indefinitely.
  • Consider requiring resolution notes (is_resolution_note_required) to capture knowledge at close-out.

7. Routes inside the integration#7-routes-inside-the-integration

  • Order routes most-specific first; evaluation is top-to-bottom, first match wins.
  • Prefer Jinja2 label/payload conditions over regex — regex route matching is deprecated and unavailable in new integrations.
  • Always end with a catch-all default route attached to a real escalation chain. Don't treat the default route as a dumping ground for alerts you want to ignore — some teams deliberately make it their *critical* path so unmatched alerts get maximum attention.
  • Audit what lands on the default route; a healthy target is ~95% of alerts matching specific routes.

8. Heartbeat monitoring: watch the watchers#8-heartbeat-monitoring-watch-the-watchers

Heartbeats are monitoring for your monitoring — a dead man's switch. IRM expects a periodic ping; if none arrives within the configured timeout (1 minute – 24 hours), it creates an alert group and escalates. When the heartbeat resumes, the alert auto-resolves.

  • Configure via the integration's More options → Heartbeat Settings; copy the heartbeat URL into the monitoring system.
  • Set the timeout longer than the monitoring interval to avoid false alerts.
  • Supported types: Alertmanager, Webhook/Formatted Webhook, ElastAlert, PRTG, Zabbix (if Heartbeat Settings isn't in the menu, the type doesn't support it). Workaround: a dedicated Webhook integration used purely as a heartbeat receiver.
  • Prometheus pattern: an always-firing rule (expr: vector(1)) routed to a heartbeat receiver with group_wait: 0s, group_interval: 1m, repeat_interval: 50s, send_resolved: false.
  • Enable for every integration where silence indicates a problem.

9. Maintenance mode#9-maintenance-mode

Suppress noise deliberately during planned work — integration page → More options → Start Maintenance:

ModeBehaviorUse for
Silence escalationsAlerts created, escalations pausedTesting integrations and templates
Group alertsEverything into one maintenance group, no escalationPlanned maintenance windows
Disable alertsPayloads ignored entirelyMajor changes

Always set a duration (it auto-disables), notify the team, and review the accumulated maintenance group afterwards.

10. Testing#10-testing

Send demo alert

verifies connectivity only — it does not test grouping, templates against real payloads, or the full ingestion pipeline. For real validation:

  1. Send actual HTTP requests (cURL or the source tool's test button) with production-shaped payloads.
  2. Repeat with the same grouping key (alert_uid for formatted webhooks) to verify grouping.
  3. Confirm the alert lands on the intended route and the escalation chain fires correctly.
  4. For Grafana Alerting, run an end-to-end test: alert rule → contact point → integration → route → chain → notification.

11. Integrations as code (Terraform and API)#11-integrations-as-code-terraform-and-api

Terraform

grafana_oncall_integration creates the integration; grafana_oncall_route adds routes. The integration's read-only link attribute exposes the endpoint URL for configuring the source tool.

terraform
resource "grafana_oncall_integration" "integration_with_templates" {
  provider = grafana.oncall
  name     = "integration_with_templates"
  type     = "webhook"
  team_id  = data.grafana_oncall_team.my_team.id

  default_route {
    escalation_chain_id = grafana_oncall_escalation_chain.default.id
  }

  templates {
    grouping_key = "{{ payload.group_id }}"
    slack {
      title     = "Slack title"
      message   = <<-EOT
          This is example of multiline template
          {{ payload.message }}
        EOT
      image_url = "{{ payload.image_url }}"
    }
  }
}

resource "grafana_oncall_route" "example_route" {
  integration_id      = grafana_oncall_integration.integration_with_templates.id
  escalation_chain_id = grafana_oncall_escalation_chain.critical.id
  routing_type        = "jinja2"
  routing_regex       = "{{ payload.severity == 'critical' }}"
  position            = 0

  slack {
    channel_id = data.grafana_oncall_slack_channel.alerts.slack_id
    enabled    = true
  }
}

Key details:

  • type values include grafana_alerting, alertmanager, webhook, formatted_webhook, datadog, zabbix, newrelic, sentry, amazon_sns, inbound_email, direct_paging, and more.
  • default_route is required (exactly one block); it takes escalation_chain_id plus optional slack/telegram/msteams blocks.
  • The templates block covers grouping_key, resolve_signal, acknowledge_signal, source_link, and per-channel appearance blocks (web, slack, telegram, microsoft_teams, email, mobile_app, sms, phone_call).
  • Routes: position starts at 0; set routing_type = "jinja2" and put the Jinja2 condition in routing_regex (regex is the deprecated default).
  • Import existing resources: terraform import grafana_oncall_integration.name "{{ id }}".

API

Auth: Authorization: Bearer <token> plus X-Grafana-URL: https://your-stack.grafana.net. Permissions: grafana-irm-app.integrations:read / :write.

  • Integrations: GET/POST {{API_URL}}/api/v1/integrations/, GET/PUT/DELETE .../<ID>/. Create body: name, type (required), team_id, templates, default_route, labels, security (["bearer_token"]).
  • Maintenance: POST .../integrations/<ID>/maintenance_start (mode: silence_escalations | group_alerts | disable_alerts; duration in seconds) and .../maintenance_stop.
  • Routes: GET/POST {{API_URL}}/api/v1/routes/ (params: integration_id, escalation_chain_id, routing_type, routing_regex, position — -1 appends), GET/PUT/DELETE .../<ID>/.

As-code best practices

  • Module per team: one module creating the team's integration, default route, severity routes, and chains together — new team onboarding becomes one module call.
  • Expose the link output so source-tool configuration (Alertmanager receivers, Datadog webhooks) can consume the endpoint URL from Terraform state instead of copy-paste.
  • Keep integrations, routes, chains, and schedules in one workspace — terraform plan shows the full alerting path for any change.
  • Manage direct paging as code too: enable manually_manage_direct_paging_integrations in IRM settings if you want team direct-paging integrations under Terraform control.
  • Git + PR review + CI: terraform plan on every PR; apply on merge; send a real test alert after applying integration or template changes.
  • RBAC on tokens: least-privilege service accounts; separate tokens for CI vs alert ingestion.

12. Quick reference checklist#12-quick-reference-checklist

  • One integration per team; source-side label selectors scope the traffic
  • Every integration named clearly and assigned to a team
  • Bearer-token protection enabled for sensitive endpoints
  • Templates add runbooks, dashboards, and severity context; tested with real payloads
  • Grouping ID stable — never status fields, timestamps, or unique IDs
  • Auto-resolution enabled where the source sends resolve signals (send_resolved: true)
  • Routes most-specific first, Jinja2 conditions, catch-all {{ True }} default with a real chain
  • ~95% of alerts matching specific (non-default) routes
  • Heartbeat monitoring on every integration where silence means trouble
  • Maintenance mode used for planned work — always with a duration
  • Real end-to-end tests, not just "Send demo alert"
  • Integrations and routes managed as code with per-team modules
